## Four-hour policy and failure recovery

Actual ARM properties.creationDate is the lifetime origin. A fresh approval ID and a fixed creation window of at most one hour must match exact-resource tags. It never uses local create intent, monotonic harness elapsed or a rolling extension. A policy must target only sqldb-gpv-mig-20261106-a1 on sql-governance-validator-dev-atiya in subscription 25ddf5d2-6e0b-4a34-82fc-bfc91415e7a6 / rg_techdemo_Atiya_Tabsum_Shaik. Production/master and arbitrary targets cannot be selected.

- Cleanup begins at **creation+3h**, leaving a one-hour safety margin. The immutable maximum is **creation+4h**. Already-expired resources are immediately attempted and logged as late. Cleanup continues after a breach; it never grants a new four hours.
- Worker state under **/home/data/gpv-sql-expiry-watchdog** records approval, target, actual creation, cleanup/deadline, attempts, retry time and observation phase. Atomic replace, fsync, private file modes and a per-pass file lock support restart recovery. Recreated resources with different creationDate, changed tags/approval or a target reappearing after absence are rejected. Lost/corrupted storage is not treated as safe permission to delete an unknown resource.
- Outer supervisor bounds each child pass to 25 seconds, SIGKILLs its process group on timeout, then retries after 10 seconds. Each HTTP call has an eight-second timeout. Persistent DELETE retry delay grows to a maximum 60 seconds. Every pass GETs the exact target before considering another DELETE. 202 and even 200/204 are never treated as completed deletion. Permissions/TLS are never relaxed.
- Known breaches are reported before network access, and the supervisor can report a stored deadline even if token/ARM work hangs. A whole-host outage or blocked shared filesystem can still prevent this reporting; no independent alert service was added.
- Logs use fixed event labels, HTTP status, attempt counts and UTC timestamps, never exception text, tokens, keys, database rows or provider content. Local stdout plus fsynced JSONL are sanitized operational logs, **not immutable independent audit storage**. Creation/deadline and observed absence/confirmation times are recorded; actual Azure DELETE completion time still requires independent Azure Activity evidence.
- run.sh has no deletion flag, and policy.json is disabled. Future arming requires both mode=armed and --permit-delete in a separately reviewed package, a fresh finite approval window and verified exact permissions. The existing rehearsal creation guard is unchanged and remains blocked.

The cloud job cannot kill a process on the laptop. A future harness must stop on the three-hour deadline, missing/stale watchdog health or a cleanup obligation; independently deleting the temporary SQL database ends its SQL availability even if the harness hangs. That harness-to-watchdog health integration is not qualified or enabled here. Do not treat this preparation as a completed test-stop interlock.
