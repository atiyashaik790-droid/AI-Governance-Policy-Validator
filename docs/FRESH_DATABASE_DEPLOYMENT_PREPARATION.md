## E–F. What this strategy changes and what remains

Historical compatible-copy/ciphertext import is unnecessary **only if the owner approves starting the replacement empty**. Keeping the source at 005 makes paired old-app/old-database rollback possible without attempting to reverse 006–008. Existing data is not deleted by this plan.

Still mandatory before production cutover:

1. Actual SQL Server empty-chain qualification, schema constraints/triggers and effective runtime permissions on the exact replacement. Local SQL compilation and SQLite cannot replace this.
2. Controlled 006/007 failure and recovery qualification under an approved, isolated procedure; previous successful tests remain reusable under their original pins. A failed fresh initialization must remain isolated and must never point the site at a partial schema. Reset/recreation is a separate destructive authorization, even for synthetic data.
3. Actual PITR proof is still absent. Backup retention/earliest-restore metadata is not a restore test. Azure PITR creates another database; a temporary recovery database still needs independently verified expiry and separate approval. See [Microsoft restore documentation](https://learn.microsoft.com/en-us/azure/azure-sql/database/recovery-using-backups?view=azuresql). No recovery gate is silently waived by selecting C.
4. Independent hard expiry/supervision remains **BLOCKED** for temporary resources. No WebJobs investigation was repeated. The proposed database is the genuinely persistent final application database, not a four-hour rehearsal renamed to evade expiry. It has ongoing cost and retention responsibilities below. Creation does not authorize any temporary clone/restore database.
5. App Service whole-settings concurrency protection is not verified. No unconditional settings replacement is prepared. Cutover needs an approved exclusive configuration writer/maintenance boundary, encrypted recoverable original settings, immediate drift checks, exact paired deployment/configuration recovery and a named available recovery operator. Local `finally` cannot guarantee restoration after host loss. Unattended configuration diagnostics remain blocked.
6. Actual Admin/User object mappings and consent/redirect/tenant settings must be confirmed without disclosing client secrets. The known Admin mapping is reusable only after approval; the intended standard User object ID is not established. Synthetic UUIDs must never be installed as real memberships.
7. The encryption key is staged; do not regenerate it. Preserve the encrypted backup and wrapping-secret custody. Current backup is protected but on the same workstation, so off-host key recovery is not proved. Key loss would make captured ciphertext unrecoverable. A fresh empty database does not cure that limitation.
8. Human Review capture/cleanup activation needs explicit approval and the healthy candidate/schema/key gate. Cleanup is application-driven (15-minute interval) and logical expiry is seven days. Outages and retained database backups prevent a hard physical-erasure-at-exactly-seven-days guarantee.
9. Real Azure OpenAI, Moderation, ADLS, Entra and runtime managed-identity acceptance remain unverified for the replacement. Configured is not VERIFIED. Separate bounded provider/export authorization is required.
