**Verified cleanup mechanism:** the candidate FastAPI lifespan starts an application-owned background worker when capture or cleanup is enabled. It immediately scans persistent SQL expiry, retries unhealthy passes after 30 seconds, otherwise runs every 900 seconds; restarts rescan persisted rows. Deletion and expiry audit commit together. It checks real database UTC time, uses conditional DELETE/returned identities, preserves unexpired rows and fails capture/reveal readiness on stale/failed worker health. This worker was locally tested and its corrected DELETE passed Azure SQL in retry-9. It is independent of the laptop when deployed to Always On App Service, but its actual hosted execution is not yet verified. It is distinct from temporary-database ARM deletion and cannot solve that expiry blocker.

Seven days means 604800 seconds: reveal denies at/after expiry even before purge. Healthy physical purge is periodic, potentially roughly 15 minutes later, longer with backlog/SQL latency. An App Service/SQL outage prevents physical deletion until recovery. Therefore **strict physical erasure exactly at seven days is not guaranteed**. SQL PITR backups may retain ciphertext after live-row purge; restoring an old backup can reintroduce expired rows, which must be denied/purged before serving. The current shared key cannot selectively cryptographically erase one expired row from backups. No logs/history/export should contain original plaintext; reveal is intentionally plaintext only to the authorized recipient. Existing metadata-only reviews cannot retroactively gain originals. If strict backup-inclusive seven-day erasure is mandatory, this implementation is not ready for that requirement; do not silently relax it.
